# Splatoon 3 Salmon Run wave lookahead core

This Rust crate implements only the parts of the Splatoon 3 **11.3.0** Salmon Run wave algorithm supported by static analysis of the owned executable and RomFS.

JobType 0/1 below describes the integrated ordinary path, not the complete JobType enum. The low-level record selector also models the no-special-state JobType 2/3 branch and the ordinary generated event/tide branch for an observed live JobType 4 mode object. The historical `thunder_scenario_generator` enum defines Regular=0, Private=1, TeamContest=2, Contest=3, and BigRun=4; the 11.3.0 executable has additional mode-dependent handling and distinct branches for values 6 and 7. The selected private scenario's actual value has not been observed.

For JobType 1, the library now conditionally predicts four special-weapon IDs by internal player index. It uses the private equipment subtype, its own RNG domain, the effective Common candidates and asset lookups, and the optional main-weapon remap. The caller must establish the live scene seed, selected branch value, candidate/lookup state, and remap inputs. The selected scenario seed has not been proven equal to the live scene seed, and internal player index has not been mapped to room join order or a network field. The JobType 1 five-row main-weapon builder is modeled separately and requires confirmed builder invocation plus effective scene ring, two pools, mode, and post-special RNG state.

The library exposes:

- Normalization of a scene's four seed words and the three implemented RNG derivations for WAVE settings, the nominal queue, and the shared normal enemy direction/species/spot stream.
- `scenario_seed` expands a nonempty, at-most-four-word logical `CoopScenario.RandomSeedAry` into the four-word game seed: missing positions repeat the **first** word, not the whole input cycle. It separately advances a supplied global xorshift state for the four-word replacement branch. A conditional resolver requires evidence that the supplied array was read, the `w28&1` gate kept it, all four words survived later setting construction, and that exact game seed was copied into the scene. It distinguishes raw scene fields from the seed that shared RNG initialization would use after all-zero normalization. The scenario array by itself does not prove the live scene seed.
- `specials::predict_private_specials` calculates the JobType 1 special list for four internal player indices from an effective scene seed, selected `G`, ordered Common candidates, and explicit asset lookup results. Low and high source branches preserve their different missing-asset behavior. An optional gate and two main-weapon rings remap the list without more RNG draws. The returned RNG state is after special selection, before later private main-weapon draws; unknown data or fewer than four resolved IDs returns an error.
- `private_weapons::predict_private_weapon_rows` continues the JobType 1 RNG immediately after special selection and builds five rows by four internal player indices. Every row reads the same logical scene main-weapon slot. Negative or missing IDs draw from the base Type0 pool; positive IDs follow the runtime mode or alternate Type0 membership check. It requires confirmed builder readiness and explicit, internally consistent effective pools. It returns packed values, cell sources, draw count, and final RNG state without claiming room join order.
- Event and tide weighted-scan operations. `draw_event` and `draw_tide` accept explicit weights and eligibility, either assembled by the caller or by the normal-path helpers below. Event and tide are separate calls because the chosen event can change tide eligibility. Reuse the same `WaveRng` across waves; skipped waves consume no draws.
- Common source weights by effective difficulty and candidate eligibility for the ordinary event/tide draw path. `event_candidates` takes the effective mode flag, stage `BanEvent` mask, raw global word and previous event. `tide_candidates` takes the selected event. A stage water override can be passed as the tide weights. For an observed nonnull runtime JobType 4 mode object, the record selector forces that flag to true; a saved scenario value alone does not prove this path. These helpers do not apply forced tide or the later one-player event override.
- `effective_difficulty_job_zero` reproduces the included-participant average with a wrapping 32-bit sum; `effective_difficulty_job_one` uses the scene Difficulty only when raw MatchMode is 11. Both clamp to 0–1665. The selected private scenario's JobType/MatchMode and JobType 0 participant records still have to be supplied.
- `predict_unforced_selections` computes event and tide for the five generated slots, or a suffix after a regeneration cutoff. Each result carries its original index. It requires per-slot effective weights and runtime candidate inputs, and applies only when the special-tide flag is disabled. A regenerated suffix starts with previous event 0 and does not consume RNG for skipped slots.
- `predict_selections` models JobType 0/1's ordinary event-then-tide scan, JobType 2/3's no-special-state path (event 0 and tide scan only), and JobType 4's ordinary event/tide scan with the mode flag forced true. For 2/3/4, the caller must establish that the runtime mode object is present and actually contains that JobType; if its pointer is null, event/tide selection uses the ordinary scan with the map-derived mode flag instead. This pointer-null equivalence covers only the low-level event/tide draw, not all WAVE behavior. JobType 0/1 special-tide state is accepted when the runtime flag is active. The caller supplies the target index and currently stored tide (0–2, or sentinel 3); the target's event and next-slot previous event are both 0. `initial_job_type_zero_special_state` computes the inspected initial JobType 0 target-3 lottery from the registered shared RNG object's optional four words and an externally established effective score. Ordinary scene initialization normalizes an all-zero scene before registering those words. On the inspected direct initial JobType 1 path, `initial_job_type_one_special_state` reports inactive because the live object's flag is first cleared. Regeneration still needs preserved state. Special state for 2/3/4 remains unsupported. JobTypes 5–7, including 7's direct `ContestRoundArray` path, are rejected. This low-level API needs effective per-wave weights and mode inputs; the high-level stage composer and nominal queue preview still cover only 0/1. WAVE application may instead use a prior tide loaded through a global pointer.
- `apply_job_one_direct_writes` projects the 11.3.0 record-application writes for JobType 1. At most one active player forces event 0; applied event 6/7 writes tide 0. A special-target gate then restores a previously stored tide read through a global singleton pointer; otherwise a separate runtime mode class 2/3 can force tide 1. The caller supplies live active-player count, that saved tide (0 when the pointer is null), special flags/target, and the mode condition. It also returns raw context word `+0x594` (game-facing name unknown). Event 5's writes are direct. This function does not model event 8's two raw context fields or its later enemy behavior; the separate helper below handles those fields conditionally.
- `project_job_one_event_eight_fields` takes the applied event, the two raw source record words, and the effective `InGame.TamaireSpanwZakoFromSpawnPoint` value. For applied event 8 with false, it returns context `+0x59c=4` and `+0x5a0=0xffffffff`; true preserves the source words. An unknown runtime value errors. This local branch does not establish event-8 enemy spawns, so the nominal queue remains unresolved.
- `choose_direction` implements the ordinary event's stage-key mask, candidate swap removal, and shared RNG draw. `predict_initial_directions` returns the WAVE-start direction and the direction after queue construction for JobType 0/1 when that queue builder runs. Stage keys must come from `CoopSpawnPointEnemy{d}` actor layers. Later direction changes require the scheduler's elapsed-time updates and the intervening draws from this shared stream, including Rare selection and spots when that queue runs. Applied Event 1 skips the ordinary Rare queue; a separate common-Zako spot draw uses director `+0x38c` and does not directly advance this direction stream. Runtime stage keys and indirect side effects still need to be established.
- Director initialization advances the domain-`0x8d56161f` state once **before** either direction selection. `predict_initial_directions` exposes the resulting shared `+0x37c` state after the two selectors and the independent initial `director_rng_38c` state expanded from that hidden output. The latter can be consumed by creation and default spot paths without directly advancing the shared Rare/direction stream.
- `direction_interval` derives the queue's direction interval from `WaveChangeNum`. `advance_direction_for_elapsed` reproduces the scheduler's signed old/new interval-crossing check and updates the direction at most once before due items in one scheduler call. The caller supplies the shared RNG after intervening boss/spot draws and the actual old/new elapsed ticks; equal-tick due items do not trigger direction draws between them.
- `rush_direction::trace_rush_directions` composes the seeded queue-ready direction with each Event 1 Rush scheduler update and returns the held group number, update flag, and shared RNG after every call. Supply the complete elapsed-tick sequence from WAVE start, positive effective `WaveChangeNum`, and runtime-equivalent stage keys. This assumes the normal JobType 0/1 queue builder ran with a nonnull stage spawner and no unmodeled callback changes `+0x37c`, held `+0x3bc`, or the keys. Rush skips ordinary Rare queue consumption, so Zako species and spot draws on separate `+0x38c` do not directly advance this direction stream. It does not establish a successful Zako spawn or a location.
- `choose_rare_boss` runs the ordinary `Rare` ID scan from a caller-supplied shared RNG state and per-ID disposition. `rare_candidate_states` builds the ID 4–14 dispositions from current signed active/reserved counters, event, global gate, and aggregated callback results. All Rare IDs have limit 3 in this selector; the count gate precedes callbacks. `normal_first_rare_candidates` is its zero-population helper for nonforced events 0/5/6. A count-limit rejection consumes a draw, while a callback rejection does not. Later bosses require refreshed counters and the intervening spot draws.
- `initial_enemy_object_rng` derives the object-local state for enemy IDs 0–31 at WAVE start. `artillery_initial_flag` and `artillery_initial_callback_allows` compute ID13's initial candidate gate from the scene seed and tide. The object-local draw does not advance the direction/species/spot stream; later flag changes are not modeled.
- `artillery_first_reservoir` replays ID13's WAVE-init flag draw and then takes the selected direction's record tides in runtime order. `artillery_reservoir_from_state` continues from a supplied object-local RNG state for later null-cached-point calls. Both use the game's f32 comparison and one local draw per matching record to report a selected record index and resulting state. The first form requires no intervening local draw; both require a null cached point. Selected records still need actor validation and fallback handling before a spot is known.
- `choose_generic_spot_index` selects from the ordered, capacity-limited actor list after the ordinary EventType 0 Rare boss's species callback declines to choose a special spot. Zero candidates consume no draw; one or more consume one shared draw. The returned index is a stage actor candidate, before individual spawn-coordinate offsets and success checks.
- `generic_rare_event_position` calculates the XYZ passed to a generic Rare creation event for all three placement channels. The caller supplies the chosen spawn actor's runtime origin/direction, live allocation counters, selected channel, and attempted ordinal. Channel 1 can add a sideways offset. It follows the game's signed counter branch and f32 operation order; raw Banc transforms and the resulting enemy actor's final initial position are not inferred.
- `OrdinaryStream` combines an event-0/5/6 nominal queue with the two initial direction draws, one direction update per actual scheduler call, periodic ID 15 selection, and interleaved Rare species / generic spot draws. Call `advance_clock(actual_elapsed_tick)` first, then `draw_next` for each due item with a fresh `EventZeroDueContext`. Its `PeriodicGoldieInput.accepted_rare_counter` is the live `director+0x4d4` value at the periodic predicate, **before** that item's possible early increment. Event 5 requires its effective Fog cycle; event 0 requires its separate cycle when the global cycle flag is active; event 6 has no periodic ID 15 force. A null runtime event pointer bypasses the periodic force, while a nonnull event must match the stream's construction event. Forced ID 15 requires an explicit `ForcedGoldieSpotGate`: over the item total limit the game still draws a spot, while at or below it an unavailable ID 15 cap/reserved slot stops before spot selection. The stream distinguishes that block from no species and an empty generic group. The caller updates counts and the counter between same-call items. For Fog, the unresolved pre-periodic indirect calls are assumed not to change shared RNG `+0x37c`; no other unmodeled code may advance it. Results are conditional draws, not confirmed enemies or final positions; a tick-4320 item may be beyond the observed WAVE end.
- `OrdinaryStream::trace_next` combines one due item's species/spot draw with `plan_ordinary_item_attempts` for ordinary ID 4–14 selections or `plan_event_zero_forced_goldie_attempts` for forced ID 15. Unknown normal-scan candidates on a nonforced item, a required cycle or forced-ID15 gate, spot, or runtime inputs return an error without advancing the stream's queue cursor or shared RNG; the caller's own callback side effects cannot be rolled back. A no-species result has zero creation calls. Forced ID 15 has its own `ForcedGoldie` result: it bypasses the ordinary Rare-total gate, uses the ID 15 pre-spot cap/reserved gate, and can call creation for ID 15 once and then ID 0 followers. The runtime callback must supply actual spot success even after a generic index is drawn, as well as the post-selected-call follower count and budget. The method replaces `AttemptInput.selected_rare_id` with the drawn ID only for ordinary Rare; forced Goldie input must explicitly identify ID 15. Feed successful registrations into the next item's fresh counters; ideal instant kills should be applied only after every item in the same scheduler call. This API remains conditional and does not establish actual spawn success.
- `EventZeroDueContext.runtime` supplies the live Rare-total, total-active, item limit, and effective item request count before one ordinary Event 0/5/6 due item. The processor checks periodic ID15 first, then the nonforced Rare-total early gate, then total-active and ID15 capacity, then the signed request-count gate before a creation-capable spot. Request count below one still permits species/spot draws on the earlier Rare-total or total-active draw-only branches. `project_event_zero_accepted_counter` returns the wrapping `director+0x4d4` value after the item: early `+1` on the nonforced Rare-total>=15 branch, late `+1` after successful spot and post-spot gate, or no change. `OrdinaryStream::trace_next_with_counter` combines this projection with the draw and reachable creation-call plan before committing its shared RNG and queue cursor. The caller feeds the returned counter into the next item and supplies fresh active counts; it must retain same-call successful registrations and apply ideal kills only between scheduler calls. Registration success, death/recount timing, and external callback effects remain caller inputs.
- `EventZeroRunner` wraps `OrdinaryStream::trace_next_with_counter` for consecutive ordinary Event 0/5/6 due items. It holds accepted `+0x4d4` separately from per-ID active/reserved, total-active, and Rare-active counts; builds fresh candidate dispositions and item limits; and requires a bounded registration receipt before the next item when creation calls were planned. Only successful ID 4–14 registration increases Rare-active; ID15 and follower ID0/1 do not. Late selected/follower active values, spot/post-spot outcomes, the follower budget, and callback results remain observed or explicitly assumed inputs. Callback decisions are supplied values, not eleven callbacks run eagerly. A late per-ID count difference blocks the next item until `reconcile_population` receives a post-item snapshot; reconciliation never rewrites accepted `+0x4d4`. The runner does not infer successful creation or automatically apply ideal kills between scheduler calls.
- `stage_data::stage_spawns` exposes a reproducible 11.3.0 snapshot of all 15 `Cop_*` packs: 331 ordinary enemy spawn actors, 139 separate Pillar anchors with 406 resolved and 3 dangling arrival links, 97 Artillery gun points, and 433 Tower arrival actors, plus raw Banc transforms, stage water overrides, and event bans. Use `available_keys()` for initial direction candidates, `group(tide, direction)` for Banc-order ordinary candidates, and `pillar_initial_static_gate()` for the WAVE-start Pillar callback's static condition. `pillar_first_untouched_anchor()` identifies the unique source anchor for 132 of 135 tide/direction groups under normal registration; three duplicate groups need runtime order. `artillery_group()` and `tower_arrival_group()` return raw source actors. These are source identities and Banc transforms, not callbacks' runtime vectors or a boss's final XYZ. On the traced normal actor-system path, successful Banc creations register synchronously and retain relative Banc order; filtering, other same-name actors, and later list changes can still shift runtime candidate indices.
- `stage_data::StageSpawns::carrier_box_sources` exposes Event 4 `CoopSpawnBoxLocator` actors in separate Low/Mid/High Banc-order lists. `carrier::predict_stage_carrier_candidate` adds f32 `(0,3,0)` to their raw positions, falls back to Low for a missing/invalid runtime tide, and runs the conditional one-attempt selector. `CarrierRandomInput::FreshTickLow32` reseeds from that attempt's observed `GetSystemTick` low word; `RetainedState` requires an independently observed Carrier state. Supply the current per-candidate slot IDs (negative means free) after the event's earlier spawn gates. The selected index/XYZ is a request candidate, not confirmed creation; a fresh-tick result's RNG cannot be reused for the next attempt. The private snapshot comparison is not bundled with this standalone crate.
- `predict_first_artillery_stage` combines ID13's initial object-local flag with the stage's static Artillery point count. If ID13 is selected in the first ordinary item, the flag permits it, the cached point is null, and no intervening local draws or mutations occurred, it returns the first spot scan's matching-record ordinal and object RNG state. Low/Mid have 83 singleton and seven doubleton tide/direction groups across the 15 stages; High has no points and the candidate gate declines it. A singleton gives a unique Banc source actor, while a doubleton requires runtime registration order. This is not callback success or a final coordinate.
- `predict_first_tower_arrival` computes ID8's first arrival-candidate count, filtered-runtime-list index, and object-local RNG state from the static stage group. It assumes normal registration, all Tower arrivals alive and unused, cleared WAVE-start usage counters, and no intervening object-local changes. The runtime actor order and later active-record or `CoopSpawnPointZako` fallback decide callback success; the index is not an actor ID or final XYZ.
- `predict_first_ordinary_rare` combines queue validation, initial and first-scheduler direction draws, static Pillar availability, the seeded Artillery flag, and the Rare reservoir scan for the first nonforced ordinary item of event 0/5/6 on effective JobType 0/1. A nonnull applied event must match the constructed event. Required periodic context is checked before normal callbacks; forced ID 15 returns `ForcedGoldieRequiresStream`. `predict_first_event_rare_species` also accepts the forced case, reporting ID 15 and its periodic source without fabricated candidate states, direction, spot, or post-species RNG. All other constructed Rare candidate callbacks return true in the owned 11.3.0 executable. These APIs require the actual tide, stage, global word, effective queue counts, first scheduler tick, standard enemy-object construction and callback registration, and a runtime mode that processes the ordinary Rare queue. Fog's unenumerated indirect prelude is assumed not to advance shared RNG. Results are conditional species decisions, not confirmed spawns. The lower-level candidate builder remains available when live callback registration differs.
- `predict_first_ordinary_rare_with_spot` continues a nonforced event-0/5/6 draw through a spot callback route; forced ID 15 needs the stateful stream and its separate pre-spot gate. On the generic route it uses the loaded stage's tide/direction group count to calculate the runtime array index and post-spot shared RNG. This requires the runtime group to contain the same number of unfiltered actors as the Banc snapshot. IDs 4/6/7/9/10/12/14 automatically use the generic route. Under normal registration and untouched Pillar state, ID11 automatically uses its callback route when every possible anchor in the requested group has an arrival, including duplicate-anchor groups. The caller supplies unresolved routes for IDs 5/8/13 or ID11 when that guarantee fails. An index or source anchor is not a final XYZ because runtime actor enumeration and individual placement remain unverified.
- `selected_wave_rare::predict_selected_job_one_first_rare` connects one original JobType 1 record index to its **directly applied** event/tide, effective Rare queue counts/branch, and first ordinary Rare species and spot draw. It returns typed statuses for queue bypass, event-8 handler, unsupported event, invalid queue, periodic forced ID15, and unresolved spot callback. The caller labels whether the supplied four words were observed as the live scene seed or merely assumed, whether direct values were observed to survive later overrides or merely assumed final, and separately labels zero initial Rare population, no pre-queue auxiliary effects, normal stage registration, and an unfiltered runtime actor group. A raw applied tide outside 0–2 or observed/direct mismatch is rejected before the species draw. The result retains generated values, count provenance and pre/post-spot RNG where known. The first actual scheduler tick and runtime periodic fields must be correct, and no unmodeled callback may advance the shared RNG. Generic spot indexes are runtime candidates, not verified XYZ or registered enemies; later same-tick items require `EventZeroRunner` rather than repeating this first-item calculation.
- `predict_stage_wave_selections` combines the selected stage, JobType 0/1 difficulty inputs, common or per-wave explicit pre-eligibility weights, live Big Run/global values, cutoff, and optional JobType 0/1 special-tide state into up to five generated event/tide selections. It reports the calculated difficulty and weight origin; with explicit weights, the difficulty is informational and does not select the weights. The caller must identify the actual loaded stage resource and supply runtime values; the result is a generated selection before application-time overrides.
- `predict_nominal_wave_preview` attaches nominal Rare queue times to generated event-0, event-5 (Fog), and event-6 (Missile) records on the JobType 0/1 path. Counts can come from explicit per-slot effective `WaveChangeNum/RareAppearNum`, or from the ROMFS three-Round source table with `min(wave_index, 2)` selection. The latter assumes the generated index matches the runtime current index, the effective Round list still has three entries, and no later difficulty update changes the counts. Queue branches are supplied per slot as build-time assumptions. Other generated events and invalid counts have per-slot statuses; regeneration cutoff slots are omitted. Event-specific species logic and separate timers remain outside this preview, so it does not assert actual boss spawns or final coordinates.
- `predict_job_one_applied_preview` combines the JobType 1 generated record, direct application writes, and nominal Rare queue by **applied** event. Each original index needs its own observed or assumed application state and later scheduler mode state; a previous applied tide or unchanged mode is not inferred from another predicted WAVE. It rejects JobType 0, distinguishes event 8's unresolved handler and the runtime mode that bypasses ordinary Rare queue consumption, and omits indices skipped by regeneration cutoff. Its queue times inherit the count and branch assumptions above and do not include event-specific extra timers or actual spawns.
- `periodic_goldie_source` checks the live director `+0x4d4` counter against event 5's resolved cycle (optionally halved by the global byte) or event 0's separate cycle when that byte is set. Event 6 does not enter either ID 15 force branch in the inspected processor. `choose_event_rare_species` uses that decision before the normal ID 4–14 scan; forced ID 15 consumes no species-selection RNG draws. The caller must supply resolved cycle values and establish that an ordered Rare item is actually processed. Event 0/5/6 spot and creation-call plans are modeled conditionally in `OrdinaryStream`; the common post-Rare Zako timer remains a separate step.
- `common_event_zero_rare_cycle` interpolates the common 11.3.0 `spl__CoopLevelsConfig.Levels[].ThanksStageRareCycle` field from an explicitly supplied effective difficulty. The nine source rows yield cycles 3 at difficulty 0–399, 4 at 400–499, 5 at 500–749, 6 at 750–999, 7 at 1000–1664, and 8 at 1665. This fills `PeriodicGoldieInput.event_none_cycle` only when the live effective setting matches the common row; runtime difficulty regeneration or a later override can change it.
- `common_fog_rare_cycle` reads the separate owned `Levels[].EventFog.RareAppearCycle` source rows and returns stock nominal cycles 3 at effective difficulty 0–199, 4 at 200–399, and 5 at 400–1665 under normal interpolation. Event 5 reads this setting from config `+0x44`; pass the returned value to `PeriodicGoldieInput.fog_cycle` only when the live effective setting matches the source row. The predicate applies the independent global flag half-cycle (3→2, 4→2, 5→3) itself. A runtime replacement can change the effective cycle.
- `ordinary_item_runtime_limits` derives a due item's signed request count and total-active limit from the effective `RareFollowerNum`, scene mode, queue-item `+8` flag, director deadline marker `+0x4e8`, and director time `+0x30`. The item flag forces `n=0`; otherwise scene mode 7 forces `n=2`; otherwise `n` is the supplied level value. The request is `n+1`, and the limit is `31−n` when the marker is `INT_MIN` or at/after director time, else `30−n`. Standard queue setup initializes the marker to `INT_MIN`, but a special branch can change it. This does not infer live active counts or the separate follower budget `+0x448`.
- `step_common_zako_timer` advances the Event 0/1/5/6 `queue+0x44` countdown once after the Rare queue path; Event 1 skips the ordinary Rare queue itself. The caller supplies the pre-countdown mode gate, a population/marker gate only if due, the effective `+0x40` reset interval only if allowed, and the effective optional post-reset gate (true when bypassed). Carry `timer_after` into the next scheduler call. A reset occurs before the later gate and cannot be undone by a failed Zako creation. `spawn_path_entered` means only that the timer path reached later Zako selection; it does not prove a creation call or registration, and this helper does not advance the Rare/direction shared RNG.
- `rush_location::trace_rush_locations` composes complete Event 1 scheduler ticks with the Rush direction trace, common timer, per-call eligible selector-draw counts, and per-call ordered runtime point snapshots. It never determines or returns a Zako species. The initial queue timer and each reached gate/selector result are explicit inputs. A nonnull selected point advances director `+0x38c` once more for the directly observed Event 1 creation-request setup before the next call; a missing, empty, or selected-null point does not. The trace returns the request-point record and separate selector, spot, and direct-post-request RNG states. An optional observed pre-selector RNG must match the carried state, and selection success with zero eligible visits is rejected. Seed-to-later-call continuity still assumes no unmodeled indirect `+0x38c` draws, and a request point is not a registered enemy or final actor XYZ.
- `wave_location::predict_job_one_wave_location` selects one JobType 1 record by its original WAVE index, combines generated and directly applied event/tide with the nominal Rare schedule, and uses the **applied** event for Zako location dispatch. Event 1 can run the multi-call Rush trace from the same supplied scene seed; an empty call list is rejected. Event 0 accepts one explicit post-selector runtime spot snapshot and returns a direction only after the spot path is reached. Absent snapshots, unsupported events, and event 8's unresolved handler have distinct statuses. It rejects a runtime route for the wrong applied event and a runtime tide inconsistent with the direct applied tide. For Event 0 multi-call tracing, use `event_zero_location` separately. Neither route predicts a Zako type, registration, or final enemy position.
- `event_zero_location::EventZeroLocationRunner` composes the ordinary Event 0 direction stream, every due Rare item, common Zako timer, and conditional request-point selection in scheduler order. Each clock call requires confirmation that the auxiliary step before Rare is inactive; that step can otherwise consume director `+0x38c`. Elapsed ticks must not decrease. The runner advances `+0x38c` once per planned Rare/follower creation request under an explicit stable-cap path assumption, regardless of registration success, and carries that state into Zako selector/spot/request draws. This does not determine a Zako species. The caller supplies per-item Rare callbacks and creation receipts, per-call timer/selector gates and ordered point groups, and a full population snapshot after a Zako creation-capable point before the next call. A live `+0x38c` observation can verify the seed-derived direct state or explicitly rebase it; the trace marks observed rebase provenance. Indirect callback draws on either `+0x38c` or direction/Rare `+0x37c` remain unclosed, so outputs are conditional request points rather than confirmed enemies or final XYZ.
- `zako_spot::predict_mode_zero_zako_spot` conditionally selects the common Zako spawn-point record for applied Event 0/1 and effective director mode 0. It requires a timer step that reaches the selector, confirmation that the stock species stage succeeded and used the ID 0/1/2 default false callback route, the live `director+0x3bc` direction at the spot call, tide, post-species `director+0x38c` RNG, ordered runtime group and two tree candidate lists, and scratch capacity. The group key is `tide+3*direction`; a missing group fails before either tree, while an empty existing group can receive tree candidates. The helper reports the selected record's origin and forward vector or a distinct no-draw/selected-null result, plus the after-spot RNG. It neither computes nor displays Zako species. The selected transform is an input to actor creation, not a guaranteed final enemy position. A four-word scene seed and static Banc actor order alone do not establish the required runtime candidate order or later scheduler direction.
- `zako_spot::stock_main_banc_spot` converts one raw `CoopSpawnPointEnemy{d}` actor from the owned normal main Banc into its initial candidate origin and forward vector. The main reader uses an identity load matrix; absent `Rotate` is zero, present angles are radians, and forward is the third column of `Rz * Ry * Rx`. This is conditional on the core actor transform remaining unchanged until the candidate builder snapshots it. Host `sinf/cosf` parity is not bit-verified. The helper does not decide whether that actor enters the runtime group, where auxiliary candidates fall, which point is selected, or the enemy actor final XYZ.
- `zako_spot::advance_zako_selector_inline_draws` advances the director `+0x38c` state once for each caller-established iterator visit that passes the active cap and has nonzero weight, without choosing or exposing a Zako species. The result is the state after the selector's **directly observed draws**. The observed iterator descriptor skips generic filter callbacks and direct cleanup, while registry count/row and cap/weight lookups have indirect calls whose `+0x38c` effects are unverified, so using the result as the complete pre-spot state requires confirming no additional consumption. A first-Rush seed composition also requires no earlier consumption after WAVE reset; a packet-facing caller must validate the supplied visit count against an observed bounded iterator snapshot.
  On the owned 11.3.0 stock table, the three common-Zako rows all have positive weights and allow an initial zero-population visit, so the directly observed offset is three draws if the live table, settings, and iterator match stock. This offset supports the location draw; it does not predict the selected species. Getter purity is established for the stock table class, while type-info callbacks and earlier RNG consumption remain unclosed.
- `step_relay_or_tamaire_zako_timer` adds the applied Event 7/8 gates around that common countdown for a confirmed nonnull scene. Relay stops before countdown when the signed total active count exceeds 28. When the timer is due, Relay requires the live candidate count at `[director+0x6f8]+0x68` and Tamaire the count at `+0x48`; zero or negative leaves the timer at zero without reset. The caller supplies those live counts and the common population/reset/callback inputs. For Relay, the active total and population decision must refer to the same director snapshot. This does not predict Relay boxes or Tamaire-specific enemies.
- `relay::initial_drop_rng_state` derives Event 7's constructor-time local drop RNG from optional shared-object words, preserving the difference between a missing object and an existing all-zero object. `relay::route_relay` conditionally selects either a nearest-box source or a drop-point-ready state from the live tide group, outer ring, mode bytes, and reference XYZ. `relay::step_drop` takes one current object-local RNG and inner-ring snapshot per drop-point trial, returning the selected raw source record, stack-local shuffle state, and RNG just before indirect dispatch. Box transforms and drop-point records are distinct 48-byte layouts. The caller must account for prior callback draws, stop at the call's requested trial count (one or two in inspected callers), and refresh snapshots after dispatch; these helpers do not establish the event's absolute time or confirm actor creation. An outer cursor at or beyond its count is an invalid snapshot rather than a normal no-attempt result.
- `tamaire::initial_candidate_rng_state` derives Event 8's WAVE-reset candidate RNG from optional shared-object words; constructor tick state is overwritten on the inspected reset path. `tamaire::choose_candidate` takes the current local RNG, selected runtime tide list, work capacity, eligible active-actor callback indices in order, cooldown marks, and current count. It returns one filtered source index and post-draw RNG, or a no-draw skip. `tamaire::lookup_source_after_gates` conditionally reads the opaque 56-byte node after the later indirect continuation, global-object check, and tide re-read. The live list order, callback timing, and actual spawn outcome remain external inputs; the candidate index is not a confirmed spawn position.
- `common_rush_enemy_appear_interval` calculates the stock Event 1 `EnemyAppearInterval` source from the owned 11.3.0 ROMFS rows under ordinary signed f32 interpolation: difficulty 0 returns sentinel -1, difficulty 40–1665 returns 10, and 1–39 are conditional interpolated values. A live nested setting override is not excluded. `nominal_rush_attempt_calls` runs the common timer from an explicitly assumed initial zero state with a nonnegative effective interval and every mode/population/post-reset gate assumed to pass; the per-WAVE queue builder clears `queue+0x44` via the 16-byte store at `0x3763370`, although an intervening write before the first scheduler call remains possible. It returns zero-based scheduler-call indices, e.g. `[0,10,20,30]` for interval 10 over 32 calls, not seconds or confirmed actor spawns. Sentinel -1 requires a resolved Round interval before use; actual Rush attempts, selected spots, and actor registration remain conditional on live state.
- `common_rush_enemy_active_max` calculates the stock Event 1 `EnemyActiveMax` source from the owned 11.3.0 ROMFS rows under the same conditional signed f32 interpolation. The rows are `-1/-1/15/17/19/22/25/32/32` at difficulties `0/40/100/200/300/400/500/1000/1665`; difficulty 41–47 yields 0 and 48 yields 1. A negative source value instructs the separate budget updater to use director `+0x444`. This helper does not compute live director `+0x448`, prove its update order, or decide whether the Zako location selector runs.
- `common_zako_population_gate_allows` computes the timer population gate from live director total-active `+0x44c` and budget `+0x448`, plus queue-object deadline marker `+0x4e8` and elapsed time `+0x30`: add one with 32-bit wrapping only when the marker is not `INT_MIN` and is earlier than time, then allow if the signed adjusted total is below the budget. These live values still need to be supplied; this does not decide the later optional callback. WAVE reset clears the director's active count and budget, while the budget update is a separate virtual entry; its order relative to first-WAVE tick0 remains unproven.
- `scenario_main_weapon_setting_ring` reconstructs the four-entry JobType 0 **setting** ring from the scenario main-weapon physical ring. It reads up to four logical entries and pads from source physical index zero, which may differ from the logical first. An empty source is indeterminate. This setting value becomes a scene `WeaponCandidateRing` only after successful unmodified setting-to-controller and controller-to-scene copies are independently established.

The following weapon preprocessing, grid, and postprocessing APIs model the default equipment subtype selected on the verified JobType 0 construction path (`0x37b7580`, RNG domain `0xa0c1474b`). JobType 1 constructs a separate subtype (`0x37b6020`, domain `0x352979a0`), so these APIs are not a JobType 1 weapon-grid prediction.

- `weapon_slot_source` reads the default equipment subtype's candidate ring (verified JobType 0) for WAVE indices 0–4 and slots 0–3. The caller supplies physical candidate IDs, ring start/count, and whether the runtime WAVE 3 override is active. It returns a nonnegative ID as a candidate requiring the game's validation callback, or identifies the standard/third random-pool branch. It does not draw a weapon or map slots to players. JobType 1 installs another subtype with different generation code.
- `weapon_rng_after_preprocess` derives the weapon RNG from the four scene seed words and advances it through the preprocessing shuffles, given the branch actually taken and the effective list sizes after descriptor/group readiness. In the low branch, a list of `N<=8` consumes `max(N−1,0)` draws. In the high branch, the first list has `A<=9`; after removing up to two entries, `second_added<=9` entries can be appended within the work-list capacity, giving `B=A−min(A,2)+second_added<=9` and a final selected list of `M=min(A,2)+min(B,2)<=4`. The three shuffles consume `max(A−1,0)+max(B−1,0)+max(M−1,0)` draws. The work list's capacity is 9; the selected output's capacity 4 is a different limit. The returned state applies only if that branch reaches all these shuffles and no indirect callback mutates the same RNG; callback side effects have not been ruled out. It does not establish the candidate IDs, pool order, or whether the 20-slot generation loop runs.
- `preprocess_weapon_candidates` accepts ordered opaque candidate-pointer identities from the source loops after descriptor/group readiness and before per-candidate asset lookup. Low mode takes at most eight and shuffles once. High mode head-inserts up to nine first-source entries, shuffles, removes up to two tail entries, head-inserts second-source entries until the work list reaches nine, shuffles, removes up to two more tails, and shuffles the selected list. It returns candidate identities and the post-shuffle RNG state. The later asset lookup can discard entries; this is not a list of final weapon IDs.
- `normal_source_candidates` and `third_source_candidates` filter the owned 11.3.0 `WeaponInfoMain` RSDB by a signed `UnlockedSeason` cap read from the same runtime field at each builder call. They retain source row indices, Versus-to-Coop references, candidate IDs, RSDB order, and source SHA-256. The returned entries are static candidates, not the effective game pools: game iterators use field index 8, sorted by signed source ID rather than RSDB row order; the owned 331 IDs are distinct. Lookup results, the cap at each call time, separate capacities, and the preprocessing lists' effective contents remain runtime inputs. Fallback IDs 20040/20900 are metadata only; the game adds one only when the effective pool is empty and has positive capacity. The generated source snapshot is included; regeneration requires the separately held source assets.
- `resolve_normal_pool` and `resolve_third_pool` sort the owned candidates by signed source ID, then apply the Season value read at each builder call and signed pool capacity. Normal resolution takes a lookup callback returning a known Coop target ID, known null, or an unknown-input error. It invokes lookup for every eligible source row before the capacity check, even when full. The result aligns full 32-bit stored IDs, draw-visible low-16-bit IDs, and source-row or fallback provenance; it preserves duplicate IDs. The game validates nonnegative candidates against the full IDs, while random draws read their low 16 bits. The shared `UnlockedSeason` setting (constructor default 1, potentially replaced by save/profile data), lookup outcomes, capacities, and unmodified 11.3.0 resource load remain preconditions.
- `build_weapon_grid` takes the post-preprocess weapon RNG, the effective scene candidate ring, resolved normal/third pools, effective rare-pool threshold, optional scene rare ring, and known asset-usability outcomes. It skips if the caller says the registry/mode path did not reach the 20-slot loop; otherwise it rejects swapped or misaligned pool data before drawing, validates nonnegative IDs against full 32-bit third-then-normal pool nodes, and fills five WAVE rows with four slots each. For WAVE 3, the game performs the pure nonnegative membership scan before the override to `-2`; the builder preserves that order. Direct accepted IDs pack as low16 with zero high bits; random replacements use the existing draw helpers and their upper flags. Errors retain draws already consumed. The returned grid is before `postprocess_weapon_grid`, assumes successful 5×4 allocation, and does not map slots to players.
- `predict_weapon_grid` composes completed weapon preprocessing, 20 packed cells, seven postprocessing draws and four de-duplicated slot lists into one conditional 5×4 result. It returns pre/post grids, slot/row source mappings and RNG states; a skipped readiness gate keeps the preprocessing state, and a build error exposes the RNG reached before failure. The caller supplies the actual scene ring, effective pools, branch/counts, threshold, asset results and one WAVE 3 override state that remained stable through both checks. These are slot sequences, not assignments to named players.
- `postprocess_weapon_grid` applies the seven weapon-RNG draws after all twenty packed weapon-node values are resolved. Each value keeps the low 16-bit weapon ID and upper source/random flags. Three draws permute the four slots identically across five rows. Three more draws exchange WAVE rows, with the WAVE 3 exchange conditionally suppressed while still consuming its draw; the last draw copies a selected row into row 4. The caller supplies the post-pool RNG state and the same runtime WAVE 3 flag. The result includes source-slot and source-row mappings. `weapon_slot_sequences` then transposes the processed grid into four slot lists and removes later values matching on the low 16 bits, including the game's skipped-neighbor behavior after removal; it retains the full packed value. This does not map slots to players. Ring source IDs cannot be passed directly as resolved node values when validation or random-pool replacement remains.
- `draw_third_pool_index` handles the `-2` branch's one shared RNG draw and multiply-high index from an explicitly supplied **post-preprocessing** weapon RNG state. Negative signed pool counts select index 0 without a draw; zero consumes a draw and also selects index 0. The function does not read the pool or claim that an empty pool pointer is safe.
- `draw_third_pool_node_value` continues the `-2` branch through the supplied effective third-pool u16 ID array and returns the ID plus full packed node value. It reports a missing selected entry rather than treating count zero as an empty pool with a fallback. This path performs no asset lookup. The packed value is the value written only if the output array has capacity.
- `choose_standard_random_pool` handles the `-1`/other-negative branch's first draw. It compares the exact f32 sample formed from RNG bits with the caller's effective threshold to choose the helper-normal or scene-rare pool. The owned Normal `spl__CoopRuleConfig` resources omit `RareMainWeaponPer`, so the constructor default f32 0.2 applies unless later overridden. It does not perform the following pool-specific draw or asset lookup.
- `draw_standard_random_node_value` continues that branch through the helper-normal or scene-rare pool, returning the resolved ID and full packed node value. It takes effective pool arrays, signed counts, a scene-rare asset-validity callback, and the weapon RNG after preprocessing and earlier slots. Helper count zero still draws and reads index zero; scene-rare count below one validates candidate `-1`. An unavailable pool entry is reported as unresolved. The returned node is the value written only if the game's 20-slot output array has room; this function does not model that capacity gate or reconstruct the pools from seed alone.
- **Nominal Rare queue times** for event IDs 0, 5, and 6 on JobType 0/1 when `2 <= WaveChangeNum <= 48` and `RareAppearNum <= 48`. When `RareAppearNum < WaveChangeNum`, the basic `WaveChangeNum` entries remain. The game-style max-heapsort determines same-tick order and may reorder equal entries. JobType 6 has an additional queue shuffle and is outside this API. The caller supplies the normal or special queue branch as an assumption. These are planned queue ticks, not actual boss spawns.
- `WaveChangeNum` and `RareAppearNum` from the 11.3.0 `spl__CoopLevelsConfig` table for an **effective difficulty** and round index 0–2. Values between the nine stored rows use the game's single-precision interpolation and integer truncation. JobType 0/1 difficulty arithmetic is implemented, but the relevant player records, selected mode, and scene fields must be supplied by the caller.
- `common_ordinary_item_request_count` calculates the standard EventType 0 individual request count for one ordinary queue item as `1 +` the effective row's interpolated `RareFollowerNum`. The selected Rare boss is attempted at most once; subsequent attempts use a separate follower ID 0 or 1, so this is not a count of Rare bosses. ID11 Pillar later forces the effective attempt budget to one. The source-row request is 2 for difficulty 0–99, 3 for 100–400, 2 for 401–450, and 1 for 451–1665, before live active-count and spawn checks. An effective-level override after interpolation would need its actual field value instead; a queue item with its `+8` flag set uses the separate one-individual path.
- `plan_ordinary_item_attempts` takes a selected Rare ID, the level-row request, live signed cap/active counters, current scene mode, and spot/post-spot gate results. It returns the number of calls to the game's creation function for the Rare boss and follower ID 0/1, including ID11's one-slot override. A call can fail before actor registration; the result is an attempt plan, not an observed spawn count. The caller must provide fresh follower active count and budget after the possible Rare call, particularly when processing multiple items in the same scheduler tick.
- `placement_allocation::preallocate_ordinary_rare` computes the three local placement-channel reservations after a successful spot and an optional post-spot gate that was bypassed or accepted. It applies the fixed-ID channel table, owned 11.3.0 enemy-info types or explicitly observed effective types, ID11's one-slot request, live signed caps/counts, and the follower budget. Its follower active count is read **before** the possible Rare creation call, unlike the later count needed by `plan_ordinary_item_attempts`. Counts 0/1 feed `generic_rare_event_position` with a separately established runtime actor transform and per-channel ordinal. This predicts a conditional creation-event coordinate, not a final enemy actor position.
- `rare_request_position::project_primary_rare_request` connects the stateful `trace_next_with_counter` result to the ordinary Rare primary creation-request XYZ. It requires the drawn generic candidate count/index, that selected actor's runtime origin/direction, and pre-create allocation counts/caps from the same due item. The result carries whether those position and allocation inputs were observed or assumed. It classifies no-species, forced-Goldie, skipped, no-primary-call, and callback-location branches without inventing coordinates. It rejects mismatched species, request counts, candidate indexes, effective budgets, and primary reservation. The private PCAP comparison is not bundled here; the game seed becoming the scene seed and the notified XYZ being a final actor position remain unproven.
- `levels::common_round_population_limits` returns the owned 11.3.0 common Round first/second-half active-enemy caps after difficulty interpolation. Its index is a source Round index 0–2; the caller must map later WAVE indices to the effective Round. `follower_budget::director_cap_after_scheduler_assignment` selects the signed first-half cap only when elapsed time is below the live halfway threshold, or takes a nonnegative event cap directly, yielding director `+0x444` at that guarded assignment. - `levels::common_round_quota_base` interpolates the owned `Round.NormaGoldenIkuraNum` source rows. `quota::job_zero_one_quota` applies the JobType 0/1 live-player scaling with signed 32-bit arithmetic; its special-WAVE input means the early-zero branch was actually taken. `quota::stock_job_zero_one_wave_quota` maps WAVE indices 3/4 to source Round 2 for the owned three-row setting and reports the source base and formula result. - `follower_budget::follower_budget_after_update` calculates the value written to director `+0x448` **when that director update runs**. The signed coefficient minimum and 32-bit wrapping product precede division by 100. The owned 11.3.0 common and present stage Water coefficients are all 100, exposed as a stock-resource constant, but a differing live value must be supplied. WAVE reset and separate scheduler/director update timing mean this calculation alone does not prove the budget present for the first tick-0 item.

The CLI accepts decimal or `0x` hexadecimal numbers for its existing unsigned fields; the optional `job0-score` field is a signed decimal i32. `schedule` prints one nominal queue; `waves` composes five **generated** event/tide records and event-0/5/6 nominal queues from four **scene** seed words:

```sh
cargo run -- schedule 1 2 3 4 0 10 30 normal
cargo run -- schedule-difficulty 1 2 3 4 0 1665 0 normal
cargo run -- waves 4 2 3 4 Cop_Carousel 1 0 0 0x10100
cargo run -- waves 1 2 3 4 Cop_Shakehighway 1 1665 0 0x10100 players=4
cargo run -- waves 1 2 3 4 Cop_Carousel 0 1665 0 0x10100 job0-score=20
```

For `waves`, the arguments after the four scene words are the exact loaded `Cop_*` resource name, observed JobType 0 or 1, supplied effective difficulty 0–1665, supplied `IsBigRun` 0/1, and supplied global word. It assumes initial five-slot generation and source ROMFS event/tide weights and queue counts. Without `job0-score`, it explicitly assumes inactive special-tide state and the normal queue branch. With `job0-score=<signed decimal i32>` on JobType 0, it normalizes an all-zero scene seed as the ordinary initial shared RNG setup does, calculates the initial target-3 lottery, and projects that special state into the generated records. For a winning lottery it uses the special nominal queue branch at target 3, conditional on runtime `+0x624` remaining set and the current index matching `+0x620`; other records use normal. The caller must supply the lottery's effective score, which is distinct from difficulty, and establish the live JobType 0 mode object. The command applies the owned stage `Water` overwrite and `BanEvent`, and displays the source Round used for each queue; WAVE indices 3/4 reuse Round 2. With `players=<1..4>` on JobType 1, it additionally shows the generated event/tide and the game's direct application writes. This treats the supplied initial count as the active-participant helper's return at every WAVE, and assumes inactive special-tide flags, no application-time mid-tide override, and a scheduler mode that processes the ordinary Rare queue. A one-player override can change the queue's event to 0; event 6/7 directly writes tide 0 only when the event remains 6/7 after that override. Event 8 retains an unresolved handler unless the one-player override first changes it to 0. Later overwrites, different active counts, actual enemy registrations, and player specials remain outside this command. A raw `CoopScenario.RandomSeedAry` is not proven to equal the live scene words. Without `players`, rows remain generated selections and nominal ticks only; neither form proves actual enemies or positions.

The single-queue CLI header labels its branch as an assumption. The difficulty form labels its difficulty as caller supplied. The other calculations are available through the library and require explicit runtime inputs. The CLI does not decode a packet, assign final weapons, or calculate final spawn coordinates. The species selector is conditional on its supplied candidates and RNG state; it does not predict every later boss. A four-word seed alone is insufficient for those results. The implementation has fixed vectors derived from the 11.3.0 disassembly and library fixtures. A private-job gameplay capture now exists, but its scene seed, applied WAVE fields and enemy event coordinates have not yet been matched to this CLI's inputs and outputs.

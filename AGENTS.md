# InkScope packet capture and player-state analysis

## Acquisition

- Use this repository's Rust `inkscope capture` as the primary live capture and decoder. Do not direct ordinary gameplay captures to the old NXCTF `capture_s3_lan_full.sh` or `capture_s3_lan_join.sh` scripts.
- Before each run, verify the actual host, active Ethernet interface, BPF access, available disk space, existing capture processes, and a new output path. `en18` was active on the macOS capture host on 2026-10-28; recheck it instead of assuming it remains correct.
- Use a private GameKey file such as `~/.config/inkscope/game_key.bin` with `--game-key-file`. Check its existence, 16-byte size, and restrictive permissions without printing its contents. Do not put a GameKey value in command arguments, logs, prompts, or documentation.
- Start before room discovery so the capture can observe `BrowseReply` and derive the Pia key. Example from this repository, after checking the interface and destination:

  ```sh
  dist/inkscope capture --interface en18 \
    --output "$HOME/captures/inkscope-player-$(date +%Y%m%d-%H%M%S).pcap" \
    --game-key-file "$HOME/.config/inkscope/game_key.bin" \
    --mode debug
  ```

- Check the timestamp of `dist/inkscope` against the source before relying on a live display. On 2026-10-28, an older dist binary showed generic Protocol 11 where the rebuilt binary recognized `PrivateSetting`; `cargo build --release --locked -p inkscope` and a verified copy from `target/release/inkscope` corrected that local binary. A running capture keeps its original executable until restarted.
- A capture started after room discovery can show `key_missing` for early Pia packets. If a continuous capture includes the same room's proof-verified BrowseRequest/BrowseReply, derive a room PiaKey from that evidence, confirm it authenticates packets in the later capture, and pass a private 0600 key file with `--pia-key-file` and the observed host `--peer`. Never print or transmit key bytes. A later discovery may let InkScope decode subsequent packets automatically; it cannot retroactively make the already printed early live rows visible.
- The current room's proof-verified PiaKey is cached at `~/.config/inkscope/pia_key.bin` (0600), with the observed peer `192.168.1.180` on 2026-10-28. Recheck the peer for each room; the IP and key can change. Live `capture` with that exact managed path and `--peer` permits an absent cache, saves a newly proof-verified key, and invalidates a loaded cache only after three peer-bound valid-Pia-header GCM failures. It then prints a rejoin notice ("Please re-enter the room") once while retaining the PCAP. `inspect` never mutates the cache. Do not print or copy raw key bytes into logs or docs.
- During development, use `./capture.sh` from InkScope to build the debug binary and monitor source inputs. It starts a new 0600 PCAP only after a successful build, keeps the preceding owned capture on build failure, and retries an unexpectedly exited owned capture with backoff. It never stops unrelated capture processes. Editing `capture.sh` itself requires restarting that script to load the new watcher logic.
- `BossRequestObservationOrder` numbers authenticated `CoopEnemySpawnNetEvent` rows with SalmonId 4–14, including possible retransmissions; it does not identify unique successful spawns. `StaticDirectionCandidate` and `StaticTideCandidate` come from a unique close match to pinned 11.3.0 Banc points, not a decoded direction wire field or confirmed runtime direction. Keep static geometry, packet observation, and actual scene state separate.
- Confirm that `tcpdump` reports `listening on <interface>` and that the exact InkScope process and new 0600 PCAP exist. A 24-byte PCAP has only a header and does not prove gameplay was captured. Stop only the process owned by this run, using its terminal's Ctrl-C or its tracked session; never kill every `tcpdump` or overwrite an earlier PCAP. Check packet count, PCAP readability, capture losses, and a hash before analysis.
- The current InkScope capture backend filters `udp and (port 35000 or port 49152)` in `crates/packet-capture/src/capture_backend.rs`. `--mode debug` changes display, not acquisition. Do not call this an unfiltered LAN capture. If evidence points to other ports, change or extend the InkScope capture path deliberately and verify the new scope before drawing conclusions.

## Player-state investigation

- Treat nameplate, special, HP, XYZ, ink, weapon, and badge data as candidate fields, not decoded facts. The older saved-capture census in `../NXCTF/docs/security/2026-10-26-s3-player-state-packet-census.md` confirms authenticated Protocol 5 `CoopSeqPlayerNetState` frames for groups 1107 and 1108 with two four-element arrays. It does not identify those arrays or establish current XYZ, weapon, or special counts.
- A one-console LAN Play room can emit discovery requests without sending player-state frames when no peer is present. A fully offline solo game may also send no player state on the observed LAN. Confirm actual packet counts and peer traffic before treating absence as a protocol result; one console alone does not map network elements to player slots. Use packet direction, timestamps, controlled in-game changes, and owned 11.3.0 ELF encoder/decoder evidence to test each field. Record the exact capture, record range, bit range, and counterexamples for any proposed meaning.
- Keep acquisition, authenticated decryption, field extraction, player-slot mapping, and Visualizer display as separate steps. Label unconfirmed fields `Unknown`; do not turn byte patterns, static candidates, or predictions into observed player status. Keep keys, private names, and raw player identifiers out of public examples.
- The 2026-10-28 user-reported clear capture has a verified `OnlineCoopSetting`→`Session 6` segment at `/Users/devonly/captures/inkscope-user-reported-clear-20261028-setting-6753-session6-19248.pcap`. Treat per-WAVE and cumulative deposit meanings as strong hypotheses until ELF/onscreen confirmation; direct-bank-only HUD counting misses 12 of these 22 observed array increases. ## Observed setting and RTT display semantics

- The confirmed Salmon states for Protocol 5 are GroupId 1104, 1107, and 1108. In text output, 1104 is rendered as `CoopSequenceNetState GroupId=1104 ...`, and 1107 / 1108 are rendered as `CoopSeqPlayerNetState GroupId=...`. `--mode normal` hides Protocol 5 rows whose GroupId cannot be confirmed, while `--mode debug` displays them. This is purely a display filter; `capture` records the exact same target packets to the PCAP in both modes. Do not infer a GroupId for 78-byte Protocol 5 variants lacking an explicit frame header by applying bit positions from known formats.
- `--mode normal` also omits `RTTProtocol` rows from text and JSONL output. `--mode debug` displays them, and `--hide-cycle` omits RTT requests and unmatched responses in debug mode. Neither option changes the packets saved to the PCAP.
- In the 2026-10-28 room capture, authenticated `PrivateSetting` carried Stage and Difficulty in separate messages: 30 Stage rows and 5 Difficulty rows in the later capture snapshot. The Difficulty values observed were 50, 75, 100, 125, and 150; this observation does not establish that the fields can never be combined in other packet forms.
- In a Random-correlated 78-byte `PrivateSetting` record, `StageId` is a 64-byte string whose bytes are all zero. The terminal prints this as `StageId=""`; JSONL retains the empty string. Do not substitute numeric `-1` or claim the Random mapping from bytes alone.
- In the 2026-10-28 user-observed Random selection, capture `inkscope-player-20261028-173124.pcap` has `PrivateSetting StageId=""` at record 50716 (17:59:47.793 JST), no intervening StageId update, then `OnlineCoopSetting StageResource=Cop_Shakedent` at record 51050 (17:59:58.592 JST). The user confirmed this was the Random-selected result, Gone Fission Hydroplant. Keep the empty lobby selector distinct from the concrete start-stage resource; do not generalize the resolved stage to other Random selections.
- Normal text renders `OnlineCoopSetting` GameFrame, StageResource, StageName, JobType, Difficulty, and each of `GameSeed[0]` through `GameSeed[3]` on its own line. It omits HeaderPacketId, HeaderCompressedFlag, PayloadBytes, TypeId, DifficultyWire, and zero LifeNumber at the user's request; `--details` and JSONL retain the decoded fields. Format GameSeed words as `0x`-prefixed, zero-padded 8-digit HEX in text; JSONL keeps decimal strings. This display does not prove GameSeed became the effective scene seed.
- `CaptureResponseDelayMs` appears only on an authenticated RTT `Type=1` response when InkScope has already seen the reverse-direction `Type=0` request with the same `OriginTick`, and the capture timestamp difference is greater than zero and at most 2 seconds. The value includes capture and peer-processing effects, so it is not a network-only RTT. `--hide-cycle` hides requests and unmatched responses but retains matched responses.
- In `inkscope-user-reported-clear-20261028-1938.pcap` (48,251 complete records), Session 5/6 appears at #5447/#5448 (19:15:13/14 JST) before OnlineCoopSetting #6753 (19:15:57), and again at #19247/#19248 (19:23:00) after the last CoopSequenceNetState #18470 (19:22:33). Both pairs follow Net 0x50/0x51 and Session 6 is client-to-host about 23–27 ms after host-to-client Session 5. The user's clear report is external screen observation; Session 6 alone is not a confirmed clear or game-end marker. The owned protocol notes describe Session 6 as returning Sequence/Acknowledgment.
